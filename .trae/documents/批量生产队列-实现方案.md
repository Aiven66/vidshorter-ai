# P0-3 批量生产队列 Batch Queue — 实现方案

## Context（为什么做这个）

现状：一次只能提交**一个**视频（`/api/videos/process` → 轮询 `.../status`）。做内容的用户手里有 5～10 条长视频时，
只能手工粘贴、等一条跑完再放下一条——这是"产能"瓶颈，也是付费用户最直接的升级理由。

本功能：**一次贴 N 个链接 → 服务端排队（限并发）→ 一个聚合进度面板 → 逐条结果 + 打包下载**。

### 生产环境实证（决定了整个设计）
- Vercel 项目 env 共 33 条，**没有 `QSTASH_TOKEN`、没有 `COZE_*`**（有 `CF_WORKER_URL`）。
  → 生产跑的是 `video-queue.ts` 的**无队列回退**：`/api/videos/process` 插行 → `fetch` 自踢 worker → 该次 invocation 内
  `runAnalyze` + 全部 clip **串行**跑完（受 `maxDuration=300` 限制）。
- 因此"排队"必须建立在**内部自踢 + DB 状态**之上，不能依赖 QStash 的 delay/parallelism。

### 已确认的范围决策
1. **与"月度积分重构"完全解耦**：不动计费模型（不做月额度、不改 Pro"无限"）。沿用"出片终态时按 `related_id=videoId` 幂等扣 `CREDIT_COST=60`"的既有扣费；本功能只在**提交前做余额预检**（明文拒绝，绝不静默截断）。
2. **门控**：付费（`starter|pro`）或 admin；free → 403 `batch_requires_paid`。有 Bearer token 时**一律服务端裁定**（不复刻 `verifyStarterEligibility` 的 clientPlan 命中即放行弱点）。
3. **队列身份不建表**：队列 = 该用户 `videos` 表中**非终态行**，按 `created_at` 升序。批次的 `videoIds` 由客户端 localStorage 记录（只用于 UI 分组与精确轮询）。**无 DB 迁移。**
4. **并发**：默认 `BATCH_CONCURRENCY=2`（env 可覆盖），单批硬上限 `BATCH_MAX_ITEMS=10`。
5. **排队泵（pump）三处触发**：提交时、前端轮询批量状态时、**worker 每条视频进入终态时（自续航：用户关掉页面队列也会继续排空）**。

## 流水线设计

```
POST /api/videos/batch/process            （Bearer；付费门控）
  1. verifyPaidEligibility              → 403 batch_requires_paid
  2. normalizeBatchUrls(body.urls)      → 400 batch_invalid_request（非法/空/超上限）
  3. 余额预检 balance = ensureDailyCreditsAndCheck() ; affordable = floor(balance / CREDIT_COST)
       balance < CREDIT_COST            → 402 batch_insufficient_credits {required, balance, affordable}
       urls.length > affordable         → 400 batch_quota_exceeded     {requested, affordable}
  4. 逐条插入 videos(status='pending', progress=0, user_id, original_url)  ← 保持输入顺序
  5. pumpUserQueue(client, userId, { minAgeMs: 0 })   ← 立即填满并发槽
  6. → { batchId, videoIds[], concurrency, affordable }

GET /api/videos/batch/status?ids=a,b,c    （Bearer）
  1. resolve user（无 token → 401）
  2. select 该用户 videos（有 ids 用之并**按 user_id 过滤**；否则最近 24h limit 30, created_at desc）
  3. pumpUserQueue(client, userId)        ← 每次轮询补位（并发满时零开销：只一次 select）
  4. → { summary, queue{concurrency,active,pending}, items[ { videoId,status,stage,progress,clips[],stalled,… } ] }

pumpUserQueue(client, userId, { concurrency, minAgeMs })
  rows     = 该用户 status ∈ (pending, processing) 按 created_at 升序 limit 50
  active   = rows 中「非终态 且 updated_at 在 SLOT_STALE_MS(8min) 内」的条数   ← 僵尸不占槽
  slots    = max(0, concurrency - active)                                    ← ≤0 直接返回
  pending  = rows 中 status='pending' && progress=0 && updated_at IS NULL
              && created_at 早于 minAgeMs 的条目（避免与提交时的踢重复）
  对前 slots 条： enqueueJob(analyze) ；返回 false → void fetch(workerWebhookUrl()) + await sleep(1500) 冲刷
  → { active, started[], pending: 剩余 }
```

### 为什么"僵尸 processing 不占槽"（关键设计）
无队列模式下，一条 invocation 要串行跑完 analyze + 全部 clip；一旦超过 300s 被 Vercel 杀掉，
视频就停在 `processing` 直到 `.../status` 的 25 分钟 STALE_MS 才被判 failed + 退费。
若把这种僵尸算作"占用并发"，队列会**停摆 25 分钟**。所以并发占用只统计"新鲜的" processing：
超过 `BATCH_SLOT_STALE_MS`(8min) 未更新的条目**不再占槽**。

**并且同一次 pump 里对它做终态对账**（`reconcileStalled`）：把僵尸行落为
`status='failed', progress=100, error_message='Processing timed out: ...'`，并对抢到转换的行调
`refundIfCharged`（幂等）——用户不应为一条被平台超时杀掉的视频付费。竞态保护：UPDATE 同时带
`status.not.in.(终态)` 与 `updated_at < cutoff`（cutoff=now-8min），三处判定（本 pump / 单视频 status / 另一个 poller）
谁抢到谁负责退费。前端对仍未对账成功的行**明文标记** `stalled`。
> 为什么必须做：前端 `stalledHint` 文案承诺"服务端会把它标记为失败"，不实现就是未兑现的用户可见承诺；
> 而单视频 status 的 25 分钟判定只在用户去轮询**那一条**视频时才触发，批量面板必须自己兜底。

### 为什么不需要批次表
`pumpUserQueue` 只依赖 `videos` 表已存在的列（`status / progress / updated_at / created_at / user_id`）
就能算出「谁在跑、还能开几条、下一条是谁」。批次分组是**展示层概念**，由客户端 `videoIds[]` 承担。
—— 省掉一次生产 DB 迁移，也避免迁移未执行导致整条链路在生产失效。

## 关键实现细节与坑

### 1. 无队列模式是生产现状 → 所有逻辑必须在自踢下成立
`enqueueJob` 返回 `false` 时，一律沿用 `/api/videos/process` **已验证**的写法：
`void fetch(workerWebhookUrl(), {method:'POST', body: JSON.stringify(msg)})` 之后 `await sleep(1500~2000)` 让出站请求冲刷完
（Vercel 在响应发出后立即冻结实例）。**不依赖 `after()`**（生产中实测不执行）。

### 2. pump 允许"重复踢"，因为有幂等兜底
`runAnalyze` 用 `.eq('progress', 0)` 做原子认领：重复投递只会白跑一次 invocation，**不会重复出片、不会重复扣费**
（扣费另有 `related_id` 幂等）。所以 `planPump` 不必追求"绝不重复"，只需保证**不超发并发**。

### 3. 绝不静默截断（沿用本项目范式）
数量超出可支付额度时**拒绝**并回传 `affordable`，由用户决定减量或升级；服务端不替用户砍数量、不砍到"能付得起的部分"。
卡片/面板上始终显示 `concurrency`、`affordable` 与 engine/门控状态。

### 4. 不动计费
提交时**只读**余额（`ensureDailyCreditsAndCheck` 会顺带做当日重置，与既有行为一致），不预扣、不冻结。
真实扣费仍发生在每条视频出片终态的 `deductCreditsOnce`。

### 5. 终态集合只有一份
`completed | partial | link_only_completed | failed` —— 从 `video-job.ts` 导出 `TERMINAL`（或在共享模块定义并由 `video-job.ts` 引用），
避免两处漂移导致"pump 认为还在跑，状态页认为已结束"。

### 6. admin 额度豁免存在既有 bug（需一并修正，否则批量 E2E 无法跑通真实出片）
`video-job.ts` L346-349 的 admin 判定是 `ADMIN_EMAILS.has(video.user_id)` —— 拿 **UUID** 去比**邮箱**，
`'demo-admin-id'` 也不是真实 UUID → **生产里任何真实管理员都按普通用户计费**：
`ensureDailyCreditsAndCheck` 给 admin 的日额度是 `PLAN_DAILY_CREDITS(null)=60=CREDIT_COST`，
即管理员**每天只能出 1 条视频**，第 2 条被 "Insufficient credits" 卡掉。
修正：改为查库 `users.role==='admin'` 豁免（与 recap-studio / export-all / cut-clip 全站门控一致）。
> 影响面：admin 不再被扣费/不再写 `daily_reset` 流水（内部账号，符合其余路由既有约定）。

### 7. 前端轮询策略
3s 一次；`document.hidden` 时降到 10s（页面在后台时没必要持续 pump）。
单次 `batch/status` 上限：ids 只接受 ≤ `BATCH_MAX_ITEMS*3=30` 个，其余忽略并回 `truncatedIds: true`（明文）。

### 8. `finally` / try 作用域既有坑
`finally` 引用的变量必须声明在 **try 外**；pump 的 `sleep/fetch` 必须包 try/catch，不得让排队失败污染出片结果。

1. **单测** `pnpm test:batch`（`node --import tsx scripts/check-batch.ts` + `node:assert/strict`）

     **超 `BATCH_MAX_ITEMS` → error（不是静默截断）**、返回顺序 == 输入顺序

     `minAgeMs` 未到的 pending 不启动；`updated_at` 已存在（已被认领）的 pending 不启动；slots > pending 时取全部
   - i18n：`batch.*` en/zh 关键 key 齐备
