# 付费墙放宽（免费用户消耗积分后可自由下载）+ 邀请裂变引导强化 — 实现方案

## 一、Context（背景与目标）

用户提出两项需求（原文）：

> 1、调整付费墙机制，平台各个功能，免费注册的用户消耗积分生成视频后，下载不再做拦截，给免费下载的机会
> 2、强化要求好友得积分的引导，激励用户邀请更多的注册用户使用

已与用户确认的 4 项决策：

1. **解锁范围 = 账号级**：只要该用户在 `credit_transactions` 中存在 `type='video_process'` 的扣费记录（即真正消耗过积分生成过视频），即视为"已消耗积分"，允许其下载/导出，不再拦截。
2. **只放开下载，不放开 Starter+ 功能**：仅调整 `verifyPaidEligibility` 路径；`verifyStarterEligibility`（竖屏 / AI 字幕 / AI 粗剪 / 拼接 / 配音 / 配乐 / 封面 / 卡拉OK / 批量队列）保持原有门控不变。免费用户导出仍为 **720p + 水印**。
3. **邀请奖励修正**：后端目前只给被邀请人（referee）发 100 积分，邀请人（referrer）实际得 0；需补齐邀请人也得 100 积分，与文案"双方各得 100 积分"一致。
4. **引导落点全选**：Dashboard 邀请卡片 + 积分不足弹窗内引导 + 左侧栏菜单项（受后台 nav-config 控制）+ 导航栏入口更醒目。

**额外发现（必须一并修复）**：前端实际使用的 i18n 是 `src/lib/i18n/index.ts`（数据源 `common.ts` + `locales/*.ts`），其中**不存在 `referral` 命名空间**。而 `ReferralDialog` 使用 `t('referral.title')` 等键 → 当前会渲染出字面量 `referral.title`。`src/lib/i18n.ts`（2960 行的旧文件）里虽然有完整 referral 文案，但已不被 `useLocale()` 使用（仅被 `blog-translate.ts` 引用 `Locale` 类型）。因此"强化引导"必须先补齐 referral 文案，否则引导弹窗文案是坏的。

### 变更 1：新增"是否消耗过积分生成"服务端判定

**文件**：`src/lib/server/export-allowance.ts`（追加，不修改既有函数）

新增导出：

```ts
/** 生成扣费流水类型（与 video-job.ts 的 deductCreditsOnce 写入保持一致）。 */
export const VIDEO_PROCESS_TX_TYPE = 'video_process';

/**
 * 账号级判定：该用户是否真正消耗过积分生成过视频。
 * 命中即视为「已消耗积分生成」→ 下载/导出门控放行（见 plan-gate）。
 * 任何失败路径 fail-closed：无法确认一律返回 false（= 未消耗，维持拦截）。
 */
export async function hasVideoGenerationSpend(userId: string): Promise<boolean> {
  const client = serviceRoleClient();
  if (!client) return false;
  try {
    const { count, error } = await client
      .from('credit_transactions')
      .select('id', { count: 'exact', head: true })
      .eq('user_id', userId)
      .eq('type', VIDEO_PROCESS_TX_TYPE);
    if (error) return false;
    return (count ?? 0) > 0;
  } catch (e) {
    console.warn('[export-allowance] spend query failed:', e instanceof Error ? e.message.slice(0, 200) : e);
    return false;
  }
}
```

**理由**：复用既有 `serviceRoleClient()` 与 `credit_transactions`，零 DDL。

### 变更 2：`plan-gate.ts` 支持"仅下载端点可因已消耗积分放行"

**文件**：`src/lib/server/plan-gate.ts`

#### 2.1 引入 `hasVideoGenerationSpend`，拆分 memo

将现有单一 `requestGrant` memo 拆成两个，避免"免费额度授予"与"基础身份裁定"互相污染：

```ts
import { getFreeExportStatus, consumeFreeExport, hasVideoGenerationSpend } from '@/lib/server/export-allowance';

/** 基础身份裁定（token 校验 + 订阅/角色）请求级 memo：不含任何额度授予语义。 */
type BaseDecision = Decision;
const baseMemo = new WeakMap<object, BaseDecision>();

/** 一次性免费导出额度的授予 memo：仅当额度命中时写入，供 commitFreeExport 消费。 */
type RequestGrant = { userId: string; committed?: boolean };
const grantMemo = new WeakMap<object, RequestGrant>();
```

`decide()` 改为：

```ts
async function decide(
  request: NextRequest,
  clientPlan: string,
  opts?: { allowSpentCredits?: boolean },
): Promise<Decision> {
  if (!isSupabaseConfigured()) {
    return clientPlan === 'starter' || clientPlan === 'pro' ? { ok: true } : { ok: false };
  }

  const token = bearerToken(request);
  if (!token) return { ok: false };

  // 基础身份裁定：请求级 memo，避免同一请求多次查库
  let base = baseMemo.get(request);
  if (!base) {
    base = await serverDecision(token);
    baseMemo.set(request, base);
  }
  if (base.ok) return base;              // 付费 / admin
  if (!base.userId) return { ok: false }; // token 有效但无法核验 → fail-closed

  // (1) 账号级「已消耗积分生成」放行 —— 仅下载/导出端点传入 allowSpentCredits
  if (opts?.allowSpentCredits) {
    const spent = await hasVideoGenerationSpend(base.userId);
    // 注意：此路径不写 grantMemo —— 不消耗一次性额度，也不连带放开 Starter+ 功能
    if (spent) return { ok: true, userId: base.userId };
  }

  // (2) 一次性免费导出额度（请求级 memo，保证只授予/消费一次）
  const granted = grantMemo.get(request);
  if (granted) return { ok: true, userId: granted.userId, freeAllowance: true };
  const status = await getFreeExportStatus(base.userId);
  if (status.available) {
    grantMemo.set(request, { userId: base.userId });
    return { ok: true, userId: base.userId, freeAllowance: true };
  }

  return { ok: false, userId: base.userId };
}
```

`commitFreeExport()` 改为读 `grantMemo`（语义不变，仅换了存储位置）：

```ts
export async function commitFreeExport(request: NextRequest): Promise<void> {
  const entry = grantMemo.get(request);
  if (!entry || entry.committed) return;
  entry.committed = true;
  let endpoint: string | undefined;
  try { endpoint = new URL(request.url).pathname; } catch { endpoint = undefined; }
  try {
    const ok = await consumeFreeExport(entry.userId, { endpoint });
    if (!ok) console.warn('[plan-gate] free export allowance commit returned false (fail-closed)');
  } catch (e) {
    console.warn('[plan-gate] commitFreeExport failed:', e instanceof Error ? e.message.slice(0, 200) : e);
  }
}
```

#### 2.2 两个门控函数签名

```ts
/** 付费（starter|pro）或 admin 才放行。下载/导出端点传 allowSpentCredits=true 以放行"已消耗积分生成"的免费用户。 */
export async function verifyPaidEligibility(
  request: NextRequest,
  clientPlan: string,
  opts?: { allowSpentCredits?: boolean },
): Promise<PaidEligibility> {
  const deny = (): PaidEligibility => ({ ok: false, reason: BATCH_ERROR_CODES.requiresPaid });
  const d = await decide(request, clientPlan, opts);
  return d.ok ? { ok: true, userId: d.userId, freeAllowance: d.freeAllowance } : deny();
}

/** Starter+ 门控：**不传 opts**，行为与现状完全一致（严格）。 */
export async function verifyStarterEligibility(
  request: NextRequest,
  clientPlan: string,
  featureKey: string,
): Promise<PaidEligibility> {
  const deny = (): PaidEligibility => ({ ok: false, reason: `${featureKey}_requires_starter` });
  const d = await decide(request, clientPlan);
  return d.ok ? { ok: true, userId: d.userId, freeAllowance: d.freeAllowance } : deny();
}
```

> 行为差异说明（有意为之）：原实现在"一次性额度命中"时写 memo，导致同请求内后续 `verifyStarterEligibility` 读缓存即放行（额度持有者可顺带用竖屏等）。新实现下 `allowSpentCredits` 路径**不写 memo**，因此"消耗过积分"的免费用户只能拿到**普通下载**，Starter+ 功能仍被拦截 —— 符合决策 2。

- `src/app/api/videos/batch/process/route.ts` L44 **保持不变**（批量生产属生成能力，不因消耗过积分而放开）。

### 变更 9：后端补发邀请人奖励（双方各得 100）

**文件**：`src/app/api/referral/reward/route.ts`

在写完 referee 奖励与流水之后（L164 之后），追加给 referrer 的奖励。幂等由"`referrals` 唯一插入成功才走到此分支"保证：

```ts
// 邀请人也得 100 积分（与产品文案「双方各得 100 积分」一致）。
// 幂等：仅在 referrals 插入成功的分支执行，同一 referee 不可能重复发奖。
const { data: referrerCredits } = await serviceClient
  .from('credits')
  .select('id, balance')
  .eq('user_id', referrerId)
  .maybeSingle();

if (referrerCredits) {
  await serviceClient
    .from('credits')
    .update({ balance: (referrerCredits.balance ?? 0) + REFERRAL_REWARD, updated_at: new Date().toISOString() })
    .eq('id', referrerCredits.id);
} else {
  await serviceClient.from('credits').insert({ user_id: referrerId, balance: REFERRAL_REWARD });
}

await serviceClient.from('credit_transactions').insert({
  user_id: referrerId,
  amount: REFERRAL_REWARD,
  type: 'referral_bonus',
  description: `Referral bonus: referred ${user.id}`,
  related_id: user.id,
});
```

响应体追加 `referrerReward: REFERRAL_REWARD`（前端 `claimReferralReward` 忽略未知字段，向后兼容）。

## 五、假设与决策

1. **"消耗过积分生成"的判定口径 = 存在 `credit_transactions{type:'video_process'}` 行**（账号级、永久）。不用 `videos` 表，因为 `videos` 含 `link_only` / 失败态且不保证已扣费。
2. **只放开下载（`verifyPaidEligibility`）**，`verifyStarterEligibility` 全部保持严格；免费导出仍 720p + 水印（服务端 `resolveExportTarget(plan)` 依据前端传入 `plan='free'`，前端继续传 `plan`，无需改）。
3. **`videos/batch/process` 不放行**：它属"批量生产（生成）"能力，若因消耗过积分而放开会破坏额度模型。
4. **`allowSpentCredits` 路径不写额度 memo**，因此不会消耗一次性额度、也不会连带放开 Starter+ 特性（比原 memo 行为更严格且更正确）。
5. **一次性免费导出额度机制保留**，对"从未生成过视频"的免费用户仍然有效（行为不变）。
6. 邀请奖励上限仍为 `MAX_REFERRALS = 5`（双方 5 次封顶）；退订/作弊场景不在本次范围。
7. 非中/英/繁语言不新增 referral 文案，自动回落英文（与现有 i18n 合并策略一致）。
